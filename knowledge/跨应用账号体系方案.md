### 2026-10-25 追加修复（提交 `9901832`，已上线 lzti-dev）

| 项 | 内容 |
|---|---|
| 配额并发双扣 | 判定「本 session 是否首个视角」的 count() 原来在事务外，同一 session 的家长视角与孩子视角并发提交时两个事务都判定为首个 → **扣两次**（免费用户只有 1 次，直接扣穿）。改为事务内 `SELECT ... FOR UPDATE` 锁 session 行后再数再判；`SessionAttempt` 加 `(sessionId, questionnaireType)` 唯一约束兜底同视角并发重复提交；`deductQuota` 改条件更新 + 影响行数，不同 session 并发也不超扣。lzti-dev 实测：并发提交两个视角，旧逻辑 `freeAttemptsUsed=2`，修复后 =1 |
| 注册接口信任前端 userId | `/api/auth/register` 的 POST 原来直接收前端传的 `userId` 与 `phone`，知道某个 PENDING 用户的 cuid 就能替他设密码、把账户转正。改为凭服务端签发的注册票据（10 分钟、限定 registration audience）推导 userId；邀请码与 SSO 各自签票，SSO 场景手机号只取票据里的已验证值 |

> 部署提醒：唯一约束需要 `prisma db push` 才会建出，生产库（`lzti`）目前**还没有**这条约束，
> 部署时必须带上 `db push` 这一步，否则并发重复提交不会被数据库挡住。

### 实施中偏离方案的地方

- **token 验签加 audience**：方案只提 issuer 校验，实际实现额外锁定 `audience = client_id`。认证服务对所有 client 用同一 issuer，不锁 audience 的话别的应用的 token 也能在这里通过验签。
- **登录页按钮按配置渲染**：`AUTH_BASE_URL` / `LZTI_REDIRECT_URI` 缺失时整个「体系账号登录」入口不渲染，避免未开通 SSO 的环境里用户点进去只拿到一段 JSON 报错。**生产上线前必须先在生产 .env 补齐这四个变量并重新构建**，否则入口不出现。
- **手机号绑定不静默覆盖**：本地手机号命中但已绑到别的体系账号时返回 409，不改绑。
- **并发首登**：授权码重复提交撞唯一约束时回查已有账户复用，不再一律报「认证失败」。
- **扣次数与写入测评记录改为同一事务**：原先先扣次数再写记录，记录写入途中抛错会白扣一次，用户被永久卡在「次数已用完」（免费用户只有 1 次，扣掉就再也测不了）。现在扣减推迟到 attempt 落库时，写不成就不会扣。

### 已知边界（未修，方案已认可或属既有设计）

- 孩子走分享链接匿名先答、家长随后登录续答同一 session 时，**不扣家长次数**（方案「边界」一节已认可）。要彻底修需要给 session 加「已计费」标记，并明确「共享 session 由谁付费」——若改成由 session 主人付费，那么家长每分享一个链接、朋友答一次就要消耗家长一次额度， viral 循环会被打死。这是产品决策，不在代码层面能定。
- ~~`/api/auth/register` 的 `userId` 由前端传入~~ —— **2026-10-25 已修**：改为凭服务端签发的注册票据推导 userId，邀请码流程与 SSO 流程各自签票，SSO 场景的手机号只取票据里的已验证值。详见「〇之五」与提交 `9901832`。

### 二、阻塞项：必须先补齐才能推生产

**1. 生产 lzti 的 SSO 环境变量一个都没有**

生产 `.env` 只有 `DATABASE_URL` / `JWT_SECRET` / `NZYY_API_URL`，缺 `AUTH_BASE_URL` / `CLIENT_ID` / `CLIENT_LZTI_SECRET` / `LZTI_REDIRECT_URI`（另缺 `JWT_ISSUER`）。

`src/app/login/page.tsx` 是服务端组件读 `process.env`，Next 会把该页静态化，**值在 build 时烘进产物**。所以必须「先补 env 再 build」，顺序不能反。缺变量的后果是安全降级——登录页不渲染「体系账号登录」入口，不报错，但等于 SSO 没上线。

**2. auth-dev 没有任何生产 client**

`AUTH_CLIENTS=wxcl-dev,lzti-dev`，密钥与回调也只配了这两套（`CLIENT_LZTI_DEV_REDIRECT_URI=https://lzti.nzyy.ltd/api/auth/callback`）。

`auth-dev/src/oauth.js` 的 `validateClient` 逐字比对 client_id / secret / redirect_uri，生产 lzti 无论配什么 client_id 都过不了。同文件还有一条启动期校验：

```js
const isProd = process.env.NODE_ENV === 'production';
if (isProd === id.endsWith('-dev')) throw new Error(`client_id "${id}" 后缀与 NODE_ENV 不符`);
```

语义是**「client_id 的后缀必须与服务运行模式一致」**：development 模式下只允许 `-dev` 后缀的 client，production 模式下只允许不带后缀的。所以一个服务实例不能同时服务 dev 与生产 client，**只能起第二个 production 模式的实例**。（本轮尝试把 `lzti`/`wxcl` 直接加进 dev 模式的实例，进程会反复崩溃退出——**这是断言在正常工作，不是故障**：它在强制「两实例」这个终局。这条校验是承重结构，不允许放宽，详见「〇之五」第三小节。）

另外 redirect_uri 被写死成 `.ltd` 域名，与生产的 `.cc` 对不上，也过不了。

**要动 auth-dev 就是在改共享认证服务并重启它**，风险面比两个应用部署大得多，应作为独立动作单独确认。

**3. 生产 wxcl 的 SSO 配置是「预埋但打不通」，且指向一个不通的域名**

`wxcl-v2/.env.local` 有 `AUTH_BASE_URL=https://auth.nzyy.cc` / `JWT_ISSUER=https://auth.nzyy.cc` / `WXCL_REDIRECT_URI=https://wxcl.nzyy.cc/api/auth/callback`，但**缺 `CLIENT_ID`** → `wxcl-v2-dev/src/lib/auth-portal.ts` 默认成 `'wxcl'`，而 auth-dev 没有这个 client。

更关键的是 **`auth.nzyy.cc` 连 DNS 记录都没有**（curl 返回 000，`getent hosts` 无输出；本机 nginx 也无其 server block，只有 `auth.nzyy.ltd` 可达，返回 200）。

wxcl 生产的 master 上目前**没有 SSO 代码**（两个 SSO 提交只在 dev-work），所以这套坏配置目前是休眠状态。**一旦把 SSO 代码合进 master 并部署，SSO 登录必然 100% 失败。**

### 三、白扣修复无法单独摘出来推生产

`2bf1522`（配额事务）与 `65ac0e5`（SSO）改的是 `assessment.service.ts` 同一段——后者引入 session 级配额单位 `isFirstAttemptInSession`，前者把它改成事务内扣减。单独 cherry-pick `2bf1522` 到 master 会丢掉 session 级配额修复。

结论：**推 master 就等于 SSO 代码同时上生产**。env 未配时是安全降级，可以接受，但生产 SSO 要真正可用，必须先完成上面第 2、3 条。

### 四、对本轮「存量零影响」表述的修正

实施记录里写「存量影响：生产 39 个用户中 36 个 expireAt=null，无人受影响」——`expireAt=null` 在 `isExpired` 中确实算未过期，这部分正确；但**漏算了 3 个 pending 用户**：`isExpired` 对 `status='pending'` 一律返回 true，部署 9e19089 后这 3 个用户会从「能用 chat 等接口」变为 403。

这是方案 §五 本来就要拦的行为（邀请码准入闸门），存量影响并非零，只是符合设计意图。

### 五、建议的推进顺序

1. **wxcl-v2-dev 重新构建部署**——开发环境配置齐全，不碰生产、不碰 auth，先把「受限落地」这个安全敞口关掉
2. **生产 SSO 作为独立一件事**：auth-dev 增加生产 client → 打通 auth 生产域名 → 补两个应用的 `.env` → 再 build + 部署
3. **lzti 生产部署**：与第 2 步绑定（推 master = 同时上 SSO 代码），若要赶白扣修复，需接受 SSO 代码先以「入口不渲染」的状态上线

## 〇之四、决策记录：账号层怎么建（2026-10-24）

> 依据「稳定、合理、安全、高效」四条底线，对「生产用户如何在认证服务上登录」给出的建议。

### 事实基础

| 通道 | 谁在用 | 身份强度 | 现状 |
|---|---|---|---|
| 门户 bind（`/bind?phone&token&from=nzyy`） | lzti 生产那 2 个 `nzyyStatus='pending'` 用户就是这么来的 | 弱，但机制不是「URL 明文」：凭据是门户 `portal_tokens` 表里存的 32 字节随机一次性 token，服务端校验；**URL 里的 phone 客户端根本不用**（lzti `/bind` 只取 token，phone 取自校验结果）。真正的弱点是**门户那层手机号墙**——门户不验证手机号，任何人输入任意号码都能换到 token | 跑得通 |
| auth-dev SSO | 只有 2 个测试账号 | 强：手机号 + 密码 | 链路齐了但无可登用户 |
| 密码哈希跨库同步（把 lzti/wxcl 的 bcrypt 哈希写进 `AuthUser`） | 无 | 强 | 技术可行：两边都是 bcrypt，`$2a$` / `$2b$` 格式兼容 |

### 建议：先做「账号层登记」，不开 SSO 入口

> 2026-10-25 订正：登记的**落点**从 auth-dev 改为新建的 `auth.nzyy.cc`（production 模式实例），
> 理由见「〇之五」第二小节；其余判断不变。「设一次密码」的入口也订正了：
> **auth 侧是 `/activate`（凭邀请 token 设密码）**，不是 lzti 的 `/sso/setup`
> ——后者是 lzti 本地的补全注册页（设 lzti 密码 + 填孩子信息）。

lzti / wxcl 用户注册成功时，**异步**向认证服务登记一条 `AuthUser`（phone + 主体 ID），**`passwordHash` 留空**——登记 ≠ 授权，没有密码就换不出 token。登记失败绝不阻塞注册（失败即忽略），只是该用户暂时用不了 SSO。将来真有人需要在另一个应用免注册时，在认证服务侧引导设一次密码（走 `/activate`，凭邀请 token），设完跨应用通用。

对着四条底线：

- **稳定** — 不动已跑通的 bind 通道，也不碰两个应用刚完成部署的登录路径
- **合理** — 三层模型要求有账号层，但现在账号层只有 2 个测试账号、真实用户一个没有，模型是悬空的。**登记是让模型成立的前提**，不是额外功能
- **安全** — 登记阶段不落任何可用凭据，密码哈希不跨系统流动
- **高效** — 一个 hook + 一个 auth-dev 接口的量级，不引入 DNS、证书、港服 nginx、第二个服务实例的运维面

**顺带解决存量回填**：回填的本质就是给存量用户各登记一条记录，同一套接口批量调一遍即可，不必单独写 backfill 脚本。

### 两个被否掉的方案

**认证服务信任门户 token** — 等于承认「知道手机号 = 你是你」。门户是手机号墙、无密码，任何拿到门户 token 的人都能登所有应用。安全上最差，且把门户重新拉回账号层，破坏分层。

**密码哈希跨库同步** — 用户在 lzti 的密码能直接在 wxcl 用，零额外交互，很诱人。但它把 auth-dev 变成凭据汇聚点：一个库泄漏 = 所有应用泄漏；且同步是异步的，认证服务抖动就会出现「注册成功但 SSO 登不上」。在用户量还小的时候，这笔复杂度换来的那一步交互不划算。

### 为什么 `auth.nzyy.cc` 是最后一步

> 2026-10-25 订正：这一步的**时机**变了——不是「开 SSO 入口前的最后一步」，
> 而是「登记 hook 上线前的前置一步」。落点从 auth-dev 改为新建的 production 实例，
> 理由是全机零备份 + dev 模式与生产身份数据不相容（见「〇之五」第二小节）。
> 「不建 auth.nzyy.cc 就开不了 SSO 入口」这个结论不变。

它只回答「生产环境能不能用 SSO」，而真正卡住的是「账号层有没有真实用户」和「用户为什么要用 SSO 而不是本地密码登录」。域名和实例建好了却没人登，等于多一套运维面、零收益。

当前状态是对的：两个应用的生产都部署了 SSO 代码但入口不渲染，账号层就绪后补 env + 建域名就能开，不用重新部署。

### 触发往下推的判据

- 出现第一个「同一个人在两个应用各注册一次并抱怨」的案例
- 或 wxcl 的拉新成本开始要求复用 lzti 已有用户

届时的动作顺序：建 `auth.nzyy.cc` → 起 production 模式的认证实例 → 启用生产 client → 开 SSO 入口。

## 〇之五、账号层不变量与落点（2026-10-25 补充）

> 本节把前文散落的判断收成可执行的不变量，并订正三处与库不符的表述。

### 一、账户诞生路径（不变量）

**认证服务侧：`AuthUser` 只有两条诞生路径。**

1. 凭邀请 token 走 `/activate` 设密码（`AuthInvite`）
2. 迁移脚本批量导入既有账户（`migrate-wxcl`）

**没有「手机号即账号」这条路。** `login.js` 与 `server.js` 的登录分支都要求 `passwordHash` 存在，登记（只写手机号、不落凭据）换不出 token——这是「登记 ≠ 授权」的机制依据。

**下游应用侧：SSO 新用户落在「身份」层，不是「账号」层。**

| 应用 | SSO 新用户落点 |
|---|---|
| lzti | `status='PENDING'` 预账户（系统发放 slot，referrer 留空）→ 补全注册转正 |
| wxcl | `active` + 3 个月起步（`source='sso'`） |

这不与上面的不变量冲突：账号由 auth 侧证明（已验证手机号 + 主体 ID），身份由各应用自己的规则决定。三层模型说的就是这件事。

**被否的路：门户 bind 通道。** 它建的用户**没有 `portalUserId`**（`api/bind/route.ts` 只写 phone 与 nzyyStatus），在账号层里是断的；而且门户自身不验证手机号，任何人输入任意号码都能换到 bind token。

**因此：SSO 入口开启时，bind 通道必须退役。** 否则两条身份通道永久并存，弱通道会被无限续命。退役的理由是「两套身份锚点」，不是「bind 的 token 弱」——bind 的凭据其实是服务端存的 32 字节随机一次性 token，机制上比文档原先描述的强。

### 二、落点：生产账户层不能放在 auth-dev

〇之四把生产账户层安置在 auth-dev 上，这个落点要改。

**理由一：这台机器上没有任何数据库备份。** crontab 里只有 acme.sh 续签，`pg_dump` 在 deploy 目录、各项目仓库、auth 服务里零命中，lzti / wxcl / nzyy_auth_dev / analytics 全都没有 dump。所以「dev 库可丢弃」不是 auth-dev 的专属纪律，而是**全机零备份**——生产身份数据放上去，一次误操作就永久丢失。

**理由二：dev 模式的运行手册与生产身份数据不相容。** `utils.js` 按 `NODE_ENV` 分叉 cookie 名，development 模式下是 `sso_session`（无 `__Secure-` 前缀）、`COOKIE_DOMAIN=.nzyy.ltd`。把生产 client 硬塞进 dev 实例，必然拿到弱 cookie 名。

**结论：落点改为新建的 `auth.nzyy.cc`（production 模式实例），auth-dev 保持 dev-only。** 成本已在〇之三核实过：通配证书在、阿里云 DNS 凭据在、四个生产 client 的 secret/redirect 已备在 `deploy/.env`。

新增的落地清单（〇之三写的是「只差 AUTH_CLIENTS 一行」，实际还差这些）：

| 项 | 说明 |
|---|---|
| 新建库 | `nzyy_auth`（生产身份库，与 dev 库物理分开） |
| DNS + nginx | 阿里云 A 记录 → 港服 nginx → 本机 |
| 实例 | production 模式进程，`NODE_ENV=production` |
| 独立 env | `JWT_ISSUER` 必须是 `https://auth.nzyy.cc`（dev 是 `.ltd`），`COOKIE_DOMAIN` 必须是 `.nzyy.cc`——两套 env 互斥，不能共用 |
| `AUTH_CLIENTS` | `wxcl,lzti`（生产 client 去掉 `-dev` 后缀） |
| 备份 | `pg_dump` 定时任务（现在一个都没有） |
| RSA 密钥 | 生产是否另起一套 keypair 待定；共用则 dev 能签发 prod token |
| **端口** | **3013**——3011 已被 wxcl-v2-dev 占用（实测在监听），auth-dev 在 3012 |

### 三、后缀断言是承重结构，不允许放宽

`auth-dev/src/oauth.js` 的启动期校验：

```js
if (isProd === id.endsWith('-dev')) throw new Error(`client_id "${id}" 后缀与 NODE_ENV 不符`);
```

〇之二把「改这条校验」列为选项之一，**这个选项要划掉**。这条断言不是挡路，是承重：它强制「一个实例只服务一种运行模式」，也就强制了「生产 auth 必须是独立实例」。放宽它等于消灭这个防呆机制。进程反复退出是它在正常工作，不是故障。

### 四、登记接口规格（下一轮实现时按此写）

接口还不存在，以下是写代码时要定死的约定：

| 项 | 约定 |
|---|---|
| 鉴权 | `client_secret`（Basic 即可，client 已注册）；无鉴权会让接口变成手机号存在性探测接口——唯一约束把 200/409 变成 oracle |
| 幂等 | **upsert**，不是 create。手机号已登记不是失败，是成功路径：返回既有 `portalUserId`，应用侧补写本地字段。基础设施失败（认证服务不可达）才记日志、可重试、不阻塞注册 |
| 主体 ID | 由 auth 生成（`AuthUser.portalUserId` 有 `@default(cuid())`），**不是应用上报自己的用户 ID**——否则两个应用在唯一字段上打架 |
| `phoneVerifiedAt` | 登记时写 `NULL`。持有密码或邀请才构成所有权证明；登记即落 verified 会稀释 SSO 下发的「已验证手机号」 |
| 审计 | 记录 `account.register` 事件（谁、哪个 client、哪个手机号） |
| 可观测 | hook 失败记 warn 日志；每周对账一次（三应用用户数 vs `AuthUser` 登记数，drift > 0 告警）。不阻塞注册 ≠ 不可见 |

## 一、为什么要分层

跨应用打通最容易犯的错，是把「账号」和「身份」当成一回事——用户在一个应用注册成功，登录另一个应用时顺手给他正式身份。后果：

- 用户被重复收「拉新费」：同一个手机号要在两个应用各注册一次、各凑一次曝光
- 付费、时长、次数等**本应用内**积累的权益被跨应用串味
- 归属统计失真，无法回答「这个用户从哪来」

所以三层分离。

## 二、三层模型

| 层 | 含义 | 载体 | 跨应用 |
|---|---|---|---|
| **账号** Account | 你是谁 | auth-dev `AuthUser`（`portalUserId`）+ 手机号 | 是，全局唯一 |
| **身份** Identity | 你在本应用里是什么 | 各应用自己的状态机 | **否** |
| **归属** Attribution | 你从谁那里来 | 各应用 referral 表 | 记录跨应用、奖励本应用发（下一轮） |

**铁律：SSO 只做第一层。** 登录态不携带任何身份、付费、时长、次数信息。
跨应用登录后，用户在每个应用里的身份**一律以该应用的本地状态为准**——在 wxcl 正式不等于在 lzti 正式。

## 三、三个应用的用户规则现状（2026-10-24 核查）

### 门户 nzyy.cc

- 身份：`portal_users`（phone unique，source='nzyy'），**无 status 字段**——门户没有正式/未正式之分
- 「注册」= 留手机号（初心测试的手机号墙），无密码、无邀请码
- 免费体验：答题免费，报告需手机号；服务端按 phone 计 `intent_tests`，每日 3 次上限
- 归属：门户无 referral 表，仅埋点层 referrer / utm
- 跳转应用：`/api/portal/generate-link` → `{目标}/bind?phone&token&from=nzyy`，token 10 分钟一次性

### wxcl（望杏成林）

- 身份：正式 = 有 `User` + 有 `expireAt`；**准入门票 = 邀请码**
- 邀请码门槛：`Apply` 达标（分享被打开 ≥10 次，且 ≥3 个贡献者各被打开 ≥10 次）→ 6 位码，7 天有效
- 时长：注册赠 6 个月（`INITIAL_MONTHS`），上限 24 个月；按月累计行为换时长
  - 分享每月 3 次 +1 月 ｜ 邀请 1 人注册 +3 月 ｜ 反馈每月 3 次 +1 月
  - 邀请人邀请成功 → `unfreezeByInvite` 解冻自己 6 个月；过期后使用从当下重新起算
- 受限：`status='pending'` 恒 `isExpired=true`，**但拦截只写在 `/api/children`（4 处）**，其余 API（records / chat / daily-care / profiles / points）不看 `expireAt` → 两道闸门（邀请码准入、时长到期）实际都不生效
- 存量：生产 39 用户；36 个 `expireAt=null`；0 个 30 天内到期；3 个 pending 全是 nzyy 跳转来的

### lzti（荔学卷）

- 身份：正式 = `status='ACTIVE'`；预账户 = `status='PENDING'`（激活 slot 后创建，2 小时内注册转正）
- 权益：次数制，扣减顺序 订阅 > 分享奖励 > 免费体验；`freeAttempts` 默认 1
- **配额单位缺陷**：目前**按 attempt 扣**（`assessment.service.ts:316-323`），而一次测评含 parent / student / teacher 三个 attempt → 现状无法实现「三方视角各答一次题」
- 归属：`Referral`（shareCode → refereeId），靠手机号间接匹配，无跨应用主体 ID
- 存量：生产 23 用户（PENDING 13 / ACTIVE 10）；**0 个付费订阅**；9 个 session 均为单 attempt

### auth-dev（认证服务）

- `AuthUser`（phone 唯一、`portalUserId` 唯一）、`AuthBinding`（provider/providerKey）、`AuthSession`、`AuthInvite`
- 手机号统一存 `+86`（`utils.js: normalizePhone`）
- 客户端注册：`AUTH_CLIENTS=wxcl-dev,lzti-dev`；密钥/回调按 `CLIENT_<ID>_<SUFFIX>` 取
- `-dev` 后缀的 client 在生产模式下会被拒绝

## 四、SSO 登录的统一规则

1. **只做认证**：回调只拿到「已验证手机号 + 主体ID」
2. **本地状态优先**：本地有该手机号账户 → 用本地状态登录；本地没有 → 落成本应用的「未正式」状态
3. **手机号归一化**：统一 11 位存库，匹配前剥掉 `+86` 前缀（auth-dev 用 `+86` 存储）

## 六、安全清单

- state：随机 16 字节，10 分钟有效，httpOnly cookie，回调逐字比对
- redirect_uri：只从服务端配置取，不接受请求传入；auth-dev 侧同样校验白名单
- 授权码换 token 一律走服务端，`client_secret` 不出服务端
- 本地会话 token 不落 URL：用一次性 httpOnly cookie 传递，兑换后立即作废（删除时必须带原 path）
- 手机号归一化，避免同一自然人被造出多个账户
- 密码不外传、不进日志
- 现有 `JWT_SECRET` 生产非默认校验保持不变
